PASOS

1. Migración (con gate de arriba). Incluí:
   - Índice único parcial en `lista_precio_valor` sobre (lista_precio_id, producto_id) WHERE
     fecha_hasta IS NULL.
   - FK de `producto_proveedor` a `producto` y `proveedor`; constraint que garantice un único
     `preferido = true` por producto (mismo patrón que otras exclusividades del sistema, ej.
     proveedor preferido / precio predeterminado).

2. Backend — motor de recálculo masivo (`recalculo_masivo`):
   - Input: porcentaje, base de cálculo (costo preferido / lista existente / valor manual),
     alcance (catálogo / rubro / marca / proveedor / lista puntual), flag de exclusión de ítems
     con precio manual reciente (definir ventana de "reciente" como parámetro, no hardcodeado).
   - Debe correr en una única transacción atómica: por cada producto alcanzado, cierra la fila
     vigente en `lista_precio_valor` (fecha_hasta = ahora) y crea una nueva (fecha_desde = ahora,
     fecha_hasta = NULL, origen = 'recalculo', referencia al id de `recalculo_masivo`).
   - Guardá el registro de `recalculo_masivo` con la cantidad de productos afectados, para
     trazabilidad.

3. Backend — vigencia (`promocion` y `cambio_programado`):
   - `promocion`: CRUD + estado calculado por fecha (programada/activa/vencida) — no dependas de
     un job para saber si está activa "para lectura", calculalo al vuelo comparando con la fecha
     actual en la consulta de precio del POS.
   - `cambio_programado`: requiere un job/scheduler que, al llegar `fecha_aplicacion`, ejecute el
     mismo motor de recálculo masivo (paso 2) y marque el registro como aplicado. Definí dónde
     vive este scheduler dentro de la arquitectura Electron actual (proceso principal) antes de
     implementarlo — confirmá conmigo el mecanismo (cron local, `setInterval` con chequeo al
     iniciar la app, etc.) si no hay un patrón ya establecido en el proyecto para jobs
     programados.

4. Backend — costo multi-proveedor (`producto_proveedor`):
   - CRUD de la relación producto-proveedor con costo y flag `preferido`.
   - Al marcar un proveedor como preferido para un producto, desmarcá atómicamente el anterior
     (mismo patrón que otros flags exclusivos ya implementados).

5. Backend — importación de costos de proveedor (`importacion_costo_proveedor`):
   - Parser de archivo (Excel/CSV) con columnas configurables por proveedor (cada proveedor
     puede tener su propio formato de archivo — no asumas un formato único).
   - Matching por `codigo_proveedor` contra `producto_proveedor` existente. Productos sin match:
     listar aparte para revisión manual, no crear productos nuevos automáticamente.
   - Al confirmar la importación, actualiza costos en bloque (misma lógica de vigencia/no
     sobreescritura que el resto del sistema si corresponde, o reemplazo directo de costo si
     `producto_proveedor` no se historiza — confirmar conmigo si el costo también necesita
     auditoría histórica o alcanza con el valor vigente).

6. UI — listado de Lista de Precios:
   - Filtros por rubro y por proveedor (usando `producto.rubro_id` y
     `producto_proveedor.preferido`).
   - Función de auditoría histórica: dado un producto y una lista, poder consultar qué precio
     estaba vigente en una fecha pasada (query sobre `lista_precio_valor` con fecha_desde ≤ X ≤

7. UI — pantalla de recálculo masivo:

8. UI — gestión de promociones y cambios programados:

9. Testing:
